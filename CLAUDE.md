# KRAKEN (CLAUDE.md)

KRAKEN is an AI-assisted reverse engineering workbench on Ghidra's engine, with a CLI, MCP server
and GUI over one command registry. Goal: Rust rewrites of binaries. Status: pre-alpha, v0.1 scope
is native PE/ELF/Mach-O. Linux x86_64 is the first platform. Repo: Adam-AtlasSoftware/kraken.

Conventions for all cards: Rust 2024 edition, stable toolchain pinned in rust-toolchain.toml;
`cargo fmt` + `cargo clippy -D warnings` clean; errors via `thiserror` in libraries, `anyhow` only
in binaries; no `unwrap()` outside tests; comments only where the code is not obvious; every new
crate is GPL-3.0-or-later in Cargo.toml. Do not commit; the main loop commits.

## Crate map

- `kraken-proto`: wire and persisted types, JSON Schema (`cargo xtask schema`, `cargo xtask samples`)
- `kraken-engine`: engine capability traits + contract suite (feature `testing`)
- `engine-ghidra` + `java/kraken-ghidra`: confined Ghidra sidecar (build: `cargo xtask ghidra-ext`)
- `kraken-confine`: confinement of child processes that run untrusted code (Landlock read-only view, no network, scrubbed environment, `Limits`, `extra_read_paths`, `deny_exec_in_dir`, `run_captured*` with a deadline); `kraken-rewrite` re-exports it in `sandbox.rs` and adds the Rust toolchain; `emulate_run` (registry, runs the project binary under `kraken-emu`, docs in `docs/emulation.md`)
- `kraken-sidecar`: the plumbing both sidecar engines share: JSON-RPC framing and the multiplexing client, the confined spawner (Landlock, seccomp, netns; Windows job object), `SpawnSpec`, `ConfinementReport`, the log sink; `engine-ghidra` re-exports it
- `engine-dotnet` + `dotnet/kraken-dotnet`: managed-code engine (ILSpy decompiler in a confined C# sidecar; methods as `Managed` locators, C# with tokens; renames and method comments are applied from the edit log by the Rust engine at render time (`Annotations`), replayed on project open; build: `cargo xtask dotnet-ext`, SDK via `dotnet/install-sdk.sh`; corpus in `corpus/dotnet`; user docs in `docs/dotnet.md`, notes in `spikes/dotnet-engine/NOTES.md`)
- `engine-native-sys`: Ghidra's C++ decompiler + Sleigh built from source (`cargo xtask native-src` fetches the pinned 12.1.4 sources into `~/.cache/kraken-dev/ghidra-src`; without them a stub is built; `cxx` is a Linux-only dependency) the license and notice texts of what it compiles in are committed in `crates/engine-native-sys/licenses` (Ghidra's `LICENSE`/`NOTICE`, zlib's license, `PROVENANCE.txt`; refreshed from the pinned archive and rendered into `THIRD-PARTY-NOTICES.md` by `cargo xtask notices`, shipped as `licenses/` by `scripts/package.sh`), and a cxx-bridged C++ shim (callback load image, symbol scope, token-recording PrintC, typed references, jump tables, C declarations and prototypes through Ghidra's grammar, noreturn, a cooperative decompile timeout and stop flag on the action break points)
- `engine-native`: JVM-free engine (ADR 0014: phases 1-3, the phase 4 mutator, phase 5 names, DWARF and rebuilt references, phase 6 PE and 32-bit x86), run by default in a confined worker process (`kraken-native-worker`, a binary of the crate, spawned through `kraken-sidecar` with a watchdog: hard per-request deadlines, crash and timeout as structured errors, restart that re-opens the program, replaying `native-state.json`, and then replays the edits and types accepted since the last save; the state directory is the only directory the worker may write; `Isolation::InProcess` for tests): ELF loader (`object`, `gimli` for `.eh_frame`; 32-bit x86 too, PIE at 0x10000), PE loader (`pe.rs`: PE32/PE32+ for x86/x86-64 with the `windows` compiler specs, `Headers` plus 8-byte section names as Ghidra, imports by name and `Ordinal_<n>` with their DLL, IAT slots pointing at synthetic `EXTERNAL` stand-ins so `call [slot]` decompiles by name, `jmp [slot]` thunks, exports, base relocations, TLS callbacks `tls_callback_<n>`, `.pdata` function starts, COFF symbol names with x86 decorations handled as Ghidra shows them, stdcall/fastcall from decorations), Win32 and MSVC runtime prototypes and Windows typedefs (`win32.rs`), data models (`ctypes::DataModel`: LP64, LLP64, ILP32; `longlong` where `long` is 4 bytes, also in the shim's core types), compiler-spec call fixups in the shim (`__x86.get_pc_thunk.bx`, named by body in stripped code) and PIC-base/`.refptr` references (`refs.rs`), MSVC demangling (`msvc-demangler`), discovery on Sleigh flow with FDE seeds, landing pads and noreturn propagation, C++ names demangled as Ghidra shows them with the mangled ones kept (`demangle.rs`, `cpp_demangle`; `mangled` on summaries and symbols, labels in the listing), DWARF types and prototypes (`dwarf.rs`), decompiler with a type store and libc prototypes, disassembly, memory, xrefs, CFG, strings, imports/exports, the analyzer job and the `Mutator` (renames and labels, comments, prototypes through the decompiler, calling conventions, function create/delete/bounds, code/data; structural edits rebuild the reference index, exports and noreturn set, `Program::reindex`; with `NativeConfig::state_dir` the applied ops, defined types and analysed signatures are saved to `native-state.json` there and replayed on reopen; `src/mutate.rs`, `tests/mutate.rs`, worker replay in `tests/worker.rs`, e2e flow in `kraken-e2e/tests/exit_criterion_native.rs`); reads only Sleigh spec files: the tree `cargo xtask native-sla` compiles from the pinned sources (`~/.cache/kraken-dev/native-sla`, byte-identical to Ghidra's), `KRAKEN_NATIVE_SPECS`, or a Ghidra install (`KRAKEN_GHIDRA_HOME`); agreement with the Ghidra fixtures in `tests/agreement.rs` (`KRAKEN_AGREEMENT_SET=corpus/pe|corpus/elf32` for the other sets), PE and 32-bit ELF in `tests/windows.rs`; discovery runs the decompiler's switch analysis on several sessions at once (`KRAKEN_NATIVE_THREADS`, `tests/parallel.rs` checks it finds what one session finds) and keeps the answers in the state directory (`discovery-cache.json`, `jumpcache.rs`) so reopening is quick; decompiles are cached until the next edit; `cargo xtask bench [engine|daemon|gui|widgets]` prints the performance tables of `docs/performance.md`; notes in `spikes/native-engine/NOTES.md`
- `engine-fake`: fixture-driven engine for tests; fixtures in `corpus/fixtures` (`kraken-record`; the PE and 32-bit ELF sets keep theirs in `corpus/pe/fixtures` and `corpus/elf32/fixtures`, `kraken-record --corpus corpus/pe`; `corpus/build.sh [elf] [pe] [elf32]` builds the sets, mingw-w64 and multilib in the Containerfile, truth by `corpus/tools/groundtruth_pe.py` and `groundtruth.py --set elf32`)
- `kraken-model`: SQLite edit log, read-sets, undo, proposals, snapshots
- `kraken-registry`: command registry (77 commands, incl. `rewrite_*`, `ai_usage`/`ai_jobs`, `undo_entry`/`undo_preview`, the `patch_*` byte-patch overlay (`patch_set`/`patch_remove`/`patch_list`/`patch_export`, apply mapping in `patchfile.rs`; `patch_from_source` plans a patch from edited decompiled C through the `SourcePatchBackend` that `kraken-rewrite` attaches with the rewrite pipeline, `source_patch.rs`) and the `RewriteBackend` trait); CLI/MCP/GUI/docs are generated from it
- `kraken-host`: config, engine factories (`HostEngineFactory` picks Ghidra, native or .NET per project: `ghidra|native|auto` from `project_create --engine` or `engine` in the config, .NET by file type; the kind, the choice and the reason are recorded in `meta.json`, selection logic in `native.rs`; `NativeEngineFactory` runs the engine in its worker with the project's engine directory as `state_dir`, in-process only with `native_in_process`), daemon client, `InferManager` holds (`krakend` keeps a model while a GUI window, a `--serve-local` run or a manual start holds it, then stops it after `grace_secs`), `[[local_models]]` and `[local_serving]` config, the `local` provider kind resolved per request, `kraken setup [--dotnet|--native]` provisioning (`docs/native-engine.md`)
- `kraken-ipc` / `krakend`: authenticated local RPC and the daemon that owns projects
- `kraken-cli` (binary `kraken`) / `kraken-mcp` (`kraken mcp`: one tool per command, plus prompts `getting-started`, `explain-function`, `name-components`, `prepare-rewrite` and resources `kraken://project/summary`, `kraken://gui/selection` (the GUI publishes it to the daemon with `gui_selection_set`), `kraken://function/{address}/decompile`, `kraken://glossary[/{term}]`; tool descriptions come from the registry's `doc` (short, with an `Example:` that `kraken-registry/tests/doc_quality.rs` checks) and `details` (reference only))
- `kraken-agent`: agent loop and providers; `kraken-assist`: the assistant (explain/overview/auto-name, glossary) over an `AssistBackend`: a model API (`ApiBackend`) or a terminal agent (`AcpBackend`), chosen by the `[provider]` table (`kind = "terminal_agent"`); one assistant, one GUI tab, one docs page (`docs/assistant.md`); `AssistBackend::complete_text` is the text-only request the rewrite pipeline uses (terminal agent: empty scratch dir, no KRAKEN MCP server, every permission request denied; optional `[rewrite]` table overrides `[provider]`); every model call goes through `Meter` (`meter.rs`: per-project `ai_usage` ledger plus a daily file, list prices in `pricing.rs` with `[pricing]` overrides, caps and budget in `[ai_limits]`), and paid work asks first (GUI dialog, CLI prompt or `--yes`)
- `kraken-eval`: evaluation harness behind `kraken eval` (tasks over the corpus scored against DWARF ground truth: name stripped functions by token overlap, find the function, strings/imports questions; any backend through `Assistant` + `Task::custom`; JSON + Markdown report with transcripts; CI mode with `engine-fake` fixtures and a stand-in script delivered as an `EvalCassette` through `ReplayProvider` or to the fake ACP agent; data in `crates/kraken-eval/data`, rewrite with `KRAKEN_EVAL_BLESS=1`; docs in `docs/assistant.md`)
- `kraken-acp`: terminal-agent host over ACP (Claude Code, Codex, Gemini CLI), Node/adapter provisioning, fake ACP agent for tests
- `kraken-infer`: supervised local inference backends (llama-server, Strata, manifest engines): several models served at once, each with its own port and key; `launch_spec` maps a model and its cards to argv and env; hardware and fit checks; the stats sampler (engine metrics, VRAM per pid, RAM over the process tree) feeding the title bar chips (`docs/local-models.md`)
- `kraken-layout`: CFG layout; `kraken-gui-widgets`, `kraken-viewmodel`, `kraken-gui` (binary `kraken-gui`)
- `kraken-rewrite`: rewrite pipeline core (ADR 0013): icicle-emu function oracle, Rust translation and spec tasks, sandboxed differential tests, `<project>/rewrite.sqlite` store, planner, `RewriteService` (the backend of the `rewrite_*` commands, attached by `krakend` and the CLI), bounded repair loop, accepted-callee reuse and stale marks, strangler export, whole-program mode (`rewrite_program`: bottom-up translation, standalone Rust crate with the `rt` libc shim in `src/runtime/rt.rs`, program-level process oracle in `process.rs`/`program.rs`, `service_program.rs`; program-level repair that traces the first differing case and re-translates the likeliest function, `blame.rs`; pointer graphs, `double` and function-pointer parameters in the call description `abi.rs`, placed identically in the emulator and the native runner); spike notes in `spikes/rewrite-loop/NOTES.md`; function-level oracle tests need a Ghidra install for the x86 SLEIGH spec, all sandboxed tests need Landlock; the `program` tests run without Ghidra (cassettes in `crates/kraken-rewrite/cassettes`, references in `crates/kraken-rewrite/references/program`)
- `kraken-emu`: emulation layer on icicle's SLEIGH CPU (pinned commit, deny.toml [sources]) for x86, x86-64, ARM/Thumb, AArch64 and RISC-V 32/64: C calling conventions per architecture (function-level calls), its own Linux user-mode syscall layer (not icicle-linux; optional sysroot via `cargo xtask emu-sysroots`), a stepping API (`session.rs`) and confined runs through `kraken-emu-run`; the `kraken-rewrite` oracle runs on it; never parses DWARF (`tests/no_debug_info.rs`)
- `kraken-py` (Python module `kraken`, PyPI name `kraken-workbench`): PyO3 over the daemon client with an in-process fallback; build with maturin (`docs/python.md`); the `python` cargo feature gates PyO3 so workspace builds need no Python
- `kraken-record`: records FakeEngine fixtures from real Ghidra; `kraken-e2e`: end-to-end tests

Tests: `cargo test --workspace`; real-Ghidra tests are `#[ignore]` and need `KRAKEN_GHIDRA_HOME`,
`KRAKEN_JAVA_HOME` and the extension built. Tests that run `kraken` binaries must set
`KRAKEN_RUNTIME_DIR` to a private dir or `KRAKEN_NO_DAEMON=1`, so they never use the real daemon.

## Key decisions

- Engine is a JVM Ghidra sidecar now, behind Rust capability traits, so a native backend can replace it piece by piece.
- The KRAKEN project DB is the source of truth for annotations; the Ghidra project is a rebuildable cache.
- Every change is a transaction in the edit log, tagged with its author (user or agent run id); undo per change or per run.
- One command registry; the CLI, MCP server, GUI and agents are all clients of the `krakend` daemon.
- Agent writes auto-apply only for additive changes.
- The sidecar is confined with Landlock on Linux and kept under daemon supervision.
- License is GPL-3.0-or-later; dependencies are restricted to the cargo-deny allowlist in `deny.toml`.
- Linux x86_64 is the first platform; Windows and macOS follow as tier 1 with real-Ghidra CI.
- Sidecar IPC is JSON-RPC with length-prefixed framing over a socketpair passed as the child's stdin; Rust types are the contract.
- Every query is paginated and size-capped to keep MCP results within token budgets.
- Analysis runs as jobs with progress, cancel and resume.
- Engine and inference backends run as supervised child processes.
- Android is out of scope for 1.0.
