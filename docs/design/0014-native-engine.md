# 0014. The native engine

Status: Accepted (phase 1 done; phase 2 done for x86-64 ELF; phase 3 done on Linux; phases 4 and 5 done)
Date: 2026-10-17

## Context

ADR 0001 chose a Ghidra sidecar first and a native engine later, behind the same capability traits. Decision 95 moves the native (JVM-free) backend up: Linux feature-completeness comes first, and a KRAKEN that needs no JVM is part of that. Windows follows on the same code, and macOS later.

Ghidra's decompiler and its Sleigh lifter are C++ (Apache-2.0) and build without the rest of Ghidra; the Makefile has `libdecomp.a` and `libsla.a` targets. What the Java side normally supplies has to come from the host: an `Architecture` with a `LoadImage` (bytes), a `Scope` (symbols), core types, and a way to get the output out. rz-ghidra (LGPL-3.0) shows that this glue works without a JVM. We use it as a reference only and copy nothing from it.

The parts that exist only in Java (loaders, the program database, auto-analysis, the data type manager, FID, the demanglers) have to be rewritten in Rust over time. Each can land separately because the engine is a set of traits.

## Decision

### Crates

- **`engine-native-sys`** builds Ghidra's decompiler core and Sleigh from the pinned source (tag `Ghidra_12.1.4_build`). `cargo xtask native-src` downloads GitHub's source archive, checks its SHA-256 (`2a858300…6cec`, recorded in `xtask/src/native_src.rs`), and extracts only `Ghidra/Features/Decompiler/src/decompile/{cpp,zlib}` and Ghidra's `LICENSE` into `~/.cache/kraken-dev/ghidra-src/Ghidra_12.1.4_build`. `build.rs` compiles the Makefile's CORE, DECCORE and SLEIGH sets plus `sleigh_arch` and `inject_sleigh` as C++17 with the `cc` crate, and the bundled zlib with `LOCAL_ZLIB`/`NO_GZIP` (Ghidra's own Windows build does the same). It leaves out the console, Ghidra-protocol, BFD and sleigh-compiler files, so the archive has no system dependencies. `KRAKEN_GHIDRA_SRC` points it at another copy. Without the sources, `build.rs` builds a stub whose `available()` is false and prints how to fetch them. The `require-native` feature makes that a build error, and `KRAKEN_NATIVE_STUB=1` forces the stub. Workspace builds therefore never fail for want of the cache, and so far only Linux builds the native library; `cxx` is a Linux-only dependency, so the stub needs no C++ toolchain on other targets.
- **A C++ shim** (`shim/kraken_shim.{hh,cc}`, our own code, GPL-3.0-or-later) is bridged with `cxx`. It contains:
  - `KrakenArchitecture`, a `SleighArchitecture` subclass. Its `LoadImage` reads bytes through a Rust callback, with read-only ranges for constant propagation.
  - The default global scope, fed with function symbols from Rust.
  - Ghidra's core type names (`int`, `uint`, `undefined8`, …).
  - A `PrintC` whose emitter writes plain text and records token spans: kind, symbol, target address and varnode. That gives decision 55's text plus token map without parsing markup.
  - Entry points: decode and flow-classify instructions, lift a range to raw p-code, decompile a function, and recover a function's switch tables with the decompiler's flow analysis.
  - Phase 2 adds: typed references per instruction (address-sized constant, read, write, narrow constant) and the registers its p-code reads and writes; jump tables as (computed jump, target) pairs; C declarations and prototypes parsed by the decompiler's own C grammar (`parse_C`, `parse_protopieces`) into its type factory and onto functions as locked prototypes; noreturn flags; and a decompile limit (below).

  Each session owns a private `Sleigh` translator. The base class would share one per language, which would tie sessions together. Ghidra exceptions are rethrown as `std::runtime_error` so they reach Rust as errors.
- **`engine-native`** implements every read capability: `Loader` (ELF through the `object` crate, `.eh_frame` through `gimli`), `Analyzer`, `FunctionLister`, `Decompiler`, `TypeStore`, `Disassembler`, `MemoryReader`, `XrefProvider`, `FlowGraph`, `StringLister` and `SymbolLister`, and the `Mutator` (below). A position-independent ELF linked at 0 is loaded at 0x100000, as Ghidra does, so addresses and anchors match Ghidra projects of the same binary. The `fn_hash` uses Ghidra's definition (SHA-256 of the body bytes in address order) and the size uses Ghidra's (the number of body addresses).
- **Run-time inputs:** only Sleigh specification files: `.ldefs`, `.pspec`, `.cspec` and compiled `.sla`. `cargo xtask native-sla` builds Ghidra's Sleigh compiler from the same pinned archive (the Makefile's `sleigh_opt` set: CORE, SLEIGH and SLACOMP, plus the bundled zlib) with the system C++ compiler, and compiles the x86 and AArch64 `.slaspec` files into `~/.cache/kraken-dev/native-sla/Ghidra_12.1.4_build`, laid out like an install. All five compiled `.sla` files are byte-identical to the ones Ghidra 12.1.4 ships. The engine looks in `KRAKEN_NATIVE_SPECS`, then that tree, then `KRAKEN_GHIDRA_HOME`, then the newest install under `~/.cache/kraken-dev/ghidra`. No JVM is started, and no Ghidra install is needed.

### Function discovery

Discovery is seeded with these:

- defined function symbols
- the entry point (named `entry` when it has no symbol)
- PLT stubs, named after the GOT slot their `jmp [rip+disp]` reads
- pointers in `.init_array`, `.fini_array` and `.preinit_array`, and `DT_INIT`/`DT_FINI`, named `_INIT_<n>`, `_FINI_<n>`, `_DT_INIT` and `_DT_FINI` when no symbol names them (Ghidra's names)
- the start of `.plt`, and in static binaries the IRELATIVE PLT entries, named after the IFUNC symbol at the resolver
- every `.eh_frame` FDE start (phase 2): FDEs exist in stripped binaries too, one per function or separated part (`main.cold`)

Recursive descent follows Sleigh's p-code flow: branch, conditional branch, call, return, computed jumps and calls. Calls to functions that never return end a block. A jump to another function's entry is a tail call. A computed jump that does not load its target from a fixed slot (so it is not a stub) triggers the decompiler's flow analysis. That analysis recovers jump tables on a partial copy of the function, and their targets join the body. The landing pads an FDE's LSDA lists in `.gcc_except_table` join the body of the function at the FDE start; nothing else reaches them.

Noreturn propagation runs discovery in rounds. Functions start out noreturn by name (`exit`, `abort`, `__cxa_throw`, …). After a round, two rules add more: a function none of whose paths returns, and that calls or tail-calls a noreturn function, is noreturn; and a callee is noreturn when a call to it is followed, past alignment padding, by another function's entry (the evidence Ghidra's discovered-noreturn analysis uses, which needs no names). The decompiler learns each new mark, the jump tables of affected callers are recovered again, and discovery reruns until the set stops growing.

After the calls are exhausted, two kinds of address are tried as function starts if they lie in code that no body covers yet:

- address-sized constants in instructions (`lea` of a function, `main` passed to `__libc_start_main`)
- pointers in data (relative-relocation addends, or aligned words for fixed-address images)

On the corpus:

- Truth recall is 100% on all 20 binaries, stripped and `-O2` builds included (phase 1: 75 to 100% on the `-O2` stripped ones).
- For `pie_list-O0` and `switch_vm-O0`, all 44 functions Ghidra recorded have the same entry, size and body hash.
- With landing pads, every `cpp_shapes-O0` function has its symbol-table size.

### Program data (phase 2)

- **References** come from the decoded instructions of every body: calls and jumps from branch targets (a tail call counts as a call), switch-table entries, reads and writes of absolute and RIP-relative memory, taken addresses (`lea`), and, like Ghidra's constant propagation, the next instruction that copies or addresses through a register loaded with an address. Pointers in relocated data slots and the lazy-binding PLT code the GOT points at are indexed too.
- **CFGs** follow Ghidra's `SimpleBlockModel`: a block ends at every flow change, calls included, and starts at branch, switch and landing-pad targets and at a recovered switch's computed jump. Edges are `fallthrough`, `jump`, `conditional_true`/`conditional_false` and `switch`; a call to a noreturn function has no fall-through edge.
- **Strings** are zero-terminated ASCII/UTF-8 and UTF-16LE runs in initialized non-executable blocks; at an address code refers to, any 7-bit run counts, as Ghidra defines strings at data references.
- **Imports and exports** mirror Ghidra's external symbols (address = PLT stub) and external entry points (global and weak definitions, the entry point, init/fini functions), one name per address.
- **Types.** The type store keeps definitions in the neutral model and mirrors them into the decompiler as C declarations in its core type names (`uint`, `undefined8`, `code`); a pointer to a type not defined yet becomes `void *`, and definitions that cannot go in yet wait and are retried. About 240 glibc and C++ runtime prototypes (`libc.rs`) are applied by name to PLT stubs and statically linked functions, so `printf(0x102004,n)` reads `printf("%d\n",n)`; a user prototype on a local function changes its own output (`int cmp_id(record *a,record *b) { return a->id - b->id; }`).
- **The analyzer job** reports `load`, `core` (references, symbols, the string scan) and `expensive` (every function through the decompiler, filling in signatures), with progress per function and cancellation between and inside decompiles.
- **Decompile limit.** The shim sets a start break point on every action of the decompile's action tree (the break points the decompiler's console uses for stepping). `Action::perform` then returns at the start of each action and resumes on the next call, so the shim checks the deadline and a stop flag between actions; past the deadline it abandons the function (`timeout`), and a raised stop flag abandons it as `cancelled`. A single long action (one pass of a rule pool on a huge function) is not split, so the limit is cooperative; phase 3's watchdog makes it hard.

Agreement with the Ghidra fixtures (`tests/agreement.rs`, recall over what Ghidra recorded, precision over ours):

- `pie_list-O0` and `switch_vm-O0` (guarded by the test): functions, bodies, CFGs (blocks, edges and kinds), callers, strings, imports and exports 100%; outgoing references 100% of those that point into the image (Ghidra's other references point into its synthetic `EXTERNAL` block), at 100% and 90% precision.
- All 20 fixtures (1100 functions): functions 98.3%, bodies 94.4%, identical CFGs 90.0% (edges 95.0%), references into the image 93.1% (precision 91.6%), callers 99.3%, strings 97.1% (precision 98.4%).

### Mutation (phase 4)

The engine keeps no program database: the KRAKEN log is the source of truth, and the engine applies its ops to the open program.

- **Function edits** change the function table and the decompiler's symbol. `rename` at a function entry renames it (an empty name, the log's undo of a rename without an old name, restores the symbol's or the `FUN_` name); at any other mapped address it sets a label, which the listing shows in its labels and in operands. `create_function` without a body walks the code from the entry with discovery's own recursive descent (switch tables included); recreating a function discovery found (undoing a delete, or a body the size of the found one) restores the found body. With a body, the body is the given range, decoded linearly; the range must contain the entry. `delete_function` removes the function and its prototype and convention. `set_function_bounds` takes a range starting at the entry; the log's empty range (undoing a bounds change) restores the found body.
- **`set_type`** on a function locks the prototype onto the decompiler's function, so its own output and its callers use it, and it becomes the listed signature (rendered with the current name). It is handed to the C grammar under a placeholder name, because KRAKEN names may hold characters C does not allow. A named function type from the type store works the same way, and the log's `undefined` (undoing a `set_type`) unlocks it again. A prototype the decompiler cannot parse (a struct by value it does not know) is refused with `invalid_argument` and the previous one stays. On a data address `set_type` defines a data item of the type's size; inside a function body it is refused, as Ghidra refuses data over code.
- **Comments** are kept per address and slot. The listing shows end-of-line, else pre, else repeatable, as Ghidra's listing does. Before each decompile the function's comments go into the decompiler's comment database: plate as header comments, pre, end-of-line and post at their statements (the printer is set to show all three; Ghidra's decompiler shows only plate and pre by default).
- **`set_calling_convention`** selects and locks one of the compiler spec's prototype models (x86-64 gcc: `__stdcall`, `MSABI`, `syscall`); an unknown name is `invalid_argument`, an empty one goes back to the default.
- **`set_code_data`**: code must decode at the address; a data item is one row of the linear listing, its mnemonic the type and, for 1, 2, 4 and 8 bytes, its value.
- **Rebuilding symbols.** A rename or a cleared prototype makes a fresh decompiler function (the scope's rename leaves the old `Funcdata` behind, and there is no way to unlock a prototype), so the engine then applies the function's prototype (a user one, else a library one), convention and noreturn mark again.
- **Checks.** Newer log schemas and managed or banked anchors are `unsupported`; an address outside the image is `not_found`. A rename whose `old_name` is not the current name is `conflict_stale_read`, as is an anchor whose function hash is neither the current body's, the found body's (edits made before a bounds change) nor the one a `create_function` carried. Re-applying an op that is in effect is `Ok`; deleting a missing function is `not_found`.
- **Saving.** Every applied op, and every type defined through the type store, goes into a journal; `save` returns `native:<count>:<hash>` as the watermark. With `NativeConfig::state_dir` set (a project's engine directory), `save` and the end of an analysis also write `native-state.json` there: the journal and the analysed signatures, keyed by the binary's SHA-256. Opening the same binary again restores the signatures and replays the journal, so a reopened project is where it was without re-running the analysis, and the registry's `rebuild` (a fresh engine directory, a full replay of the log) starts from nothing. `NativeStats` reports the journal length and how many saved entries failed to replay.

The contract suite, mutation included, passes on `pie_list-O0` and `switch_vm-O0` in both isolation modes, and `kraken-e2e/tests/exit_criterion_native.rs` runs the exit-criterion flow (agent renames and retypes over MCP, user-accepted delete and recreate, undo, rebuild with no drift, each step on a freshly opened project) against native-engine projects, with the engine in its worker.

In worker mode (the default) the mutator runs in `kraken-native-worker` like every other capability: `apply`, `save` and `define_type` are worker methods, and the state directory is passed to the worker and added to its Landlock read-write set (it is created first, and it is the only directory besides the worker's private home that the worker may write). The parent keeps the ops and type definitions the worker accepted since the open, in order. A restarted worker re-opens the program, which replays `native-state.json`; the parent then compares the worker's journal length with the one at open and replays only the entries the state file does not hold yet, so nothing is lost and nothing is applied twice. Edits and saves are serialized on the parent side so the two journals stay in the same order.

### The confined worker (phase 3)

The library keeps global state and is not thread-safe, so every call takes one process-wide lock in `engine-native-sys`, and the engine runs calls on blocking threads. Phases 1 and 2 ran it in the engine's process (in practice, `krakend`); phase 3 moves it out.

`NativeEngine` now runs the program in a child process, `kraken-native-worker` (a binary of `engine-native`), by default. The split is above `Session`, not at it: the worker runs the whole in-process engine (`InProcessEngine`: loader, discovery, reference index, type store, decompiler) and answers one JSON-RPC method per capability call, so the image callback never crosses the process boundary and no query pays a round trip per instruction. The parent keeps only what it needs to rebuild a worker: the open binary, its loader spec and state directory, and the edits and type definitions accepted since the open (see Mutation for how they are replayed).

- **Confinement** is the Ghidra sidecar's, through `kraken-sidecar`'s spawner: a scrubbed environment (`HOME`, `TMPDIR`, `LANG` only), Landlock (read-only: the worker executable, the spec tree, the binary, the system library directories; read-write: a private temporary home and the state directory, if any), TCP denial and scoping, the seccomp filter that refuses `socket(2)` and every non-`AF_UNIX` `socketpair(2)`, a user and network namespace when the host allows it, and `PR_SET_PDEATHSIG`. The protocol is the sidecar framing on the socketpair that is the worker's stdin. Spawning fails unless the confinement is available, as for the other sidecars.
- **Watchdog.** Every request has a hard deadline: the decompile limit plus a grace period for `decompile`, a longer one for `open`, a default for the rest, and for an analysis job the gap between two progress events. Past it the parent kills the worker and answers `timeout` with details `{worker: "killed", method, deadline_ms}`. A worker that dies answers its requests with `internal` and details `{worker: "crashed", method, exit_code, signal, log_tail}`. Either way the next request starts a new worker, which re-opens the binary (replaying `native-state.json`) and replays the edits and type definitions the state file does not hold. A cancelled request is cancelled in the worker (`cancel {op}`); if it has not stopped within a grace period the worker is killed too, so cancellation is hard as well.
- **Core dumps.** The worker marks itself non-dumpable unless asked (`WorkerOptions::core_dumps`): on a host with `systemd-coredump` writing the core keeps the dying process, and so its channel, open for seconds, which would turn a crash into a timeout.
- `Isolation::InProcess` keeps the old behaviour for tests and for hosts without the worker binary; non-Unix platforms always run in-process for now.

### Names, DWARF, rebuilt references and licensing (phase 5)

- **C++ names** are demangled with `cpp_demangle` (MIT/Apache-2.0, already in the lockfile through `addr2line`) the way Ghidra names symbols (`demangle.rs`): the last component of the demangled name (`capacity` for `std::__cxx11::basic_string<...>::capacity() const`), spaces as underscores (`_M_construct<char_const*>`) except after `operator`, where Ghidra uses a dot (`operator.new`), ABI tags dropped, `std::string`'s constructors as `string`/`~string`, and fixed names for special symbols (`vtable`, `typeinfo`, `typeinfo-name`). This applies to functions, PLT stubs, imports and exports. The mangled name stays available: `mangled` on `FunctionSummary` and `SymbolEntry` (and on the registry's function and symbol views), and the listing shows every symbol-table name at a function entry as a label next to the function's, as Ghidra's does (`_ZNK4Rect4areaEv`, `area`). Discovery and the library prototype table still match on the symbol-table names (`_ZSt9terminatev` never returns).
- **DWARF** (`dwarf.rs`, `.debug_info` through `gimli`): structs, classes, unions, enums and typedefs go into the type store (base classes as `super_<Base>` fields; empty bases, which take no bytes, and bitfields left out), and every defined subprogram gives its function the DWARF name (spaces as underscores: `operator_new`, as Ghidra names it) and a prototype that is locked onto the decompiler's function: parameter names and types, `this`, references as pointers, varargs, noreturn, the parameters of the abstract origin for out-of-line instances (a destructor's `__in_chrg`), and a class returned in memory as `T * f(T * __return_storage_ptr__, ...)`. The listed signature uses Ghidra's spelling of the type names (`vector<double,_std::allocator<double>_>`); the decompiler's C grammar needs identifiers, so the type store and the decompiler use the names with underscores (`vector_double__std__allocator_double___`), and a second, different type of one name gets `_conflict<n>` (shown as `.conflict<n>` only when both are in the same scope, as Ghidra does). Ghidra's C grammar renames the type a typedef names, so a typedef of a named type is an alias in the type store and is not declared to the decompiler. `cmp_id` decompiles as `int cmp_id(record *a,record *b) { return a->id - b->id; }` with no user prototype. A stripped binary (or `use_symbols` off) has no DWARF.
- **Rebuilding after structural edits.** `create_function`, `delete_function`, `set_function_bounds`, `set_code_data`, `rename` and `set_type` rebuild the reference index, the exports and the noreturn set (`Program::reindex`; a replay on open rebuilds once at the end). The index covers the current bodies plus code no function holds any more, which stays code as in Ghidra (so the calls into a deleted function stay listed, without a callee name, until data is defined over them), and addresses defined as code; data defined over code drops its references. A created function's references are indexed and its callers name it. An export follows a renamed or recreated function (it is the same symbol). Functions whose bodies changed since discovery are judged by the propagation rule (no path returns and a call reaches a function that never returns), the found set holds for the others, and the decompiler and the CFGs learn the changes.
- **Licensing.** The binaries link Ghidra's decompiler and Sleigh (Apache-2.0) and Ghidra's zlib 1.3.1 subset (zlib License). `cargo xtask native-src` now also extracts Ghidra's `NOTICE` and `licenses/zlib_License.txt`; `cargo xtask notices` refreshes `crates/engine-native-sys/licenses` (Ghidra's `LICENSE` and `NOTICE`, the zlib license and Ghidra's note on its subset, and `PROVENANCE.txt` with the tag, archive URL, SHA-256 and the zlib version read from `zlib.h`) from the pinned archive when it is cached, and renders their texts into `THIRD-PARTY-NOTICES.md` whenever a shipped binary links `engine-native-sys`. Tests check that the committed copies match the archive (skipped without it), that the page names both components, and that the page is current. `scripts/package.sh` ships the directory as `licenses/`, refuses to package without those texts, and ships `kraken-native-worker` when it was built; the release workflow fetches the pinned sources and builds the Linux binaries with `require-native`, so the Linux archive carries the native engine.

## Phases

1. **Done:** source fetch and build, shim, ELF loader, discovery, decompile with tokens, disassembly, memory, Sleigh lifting (`NativeEngine::lift`), and the contract-suite subset. x86-64, with AArch64 working on a hand-built binary.
2. **Feature parity for the read side.** Done for x86-64 ELF: xrefs, CFG, strings, imports and exports, the type store fed to the decompiler, library prototypes, landing pads, noreturn propagation, the analyzer job, the decompile limit, and the `.sla` compiled from the pinned sources. The whole contract suite except mutation passes. Left for a phase 2b: PE and Mach-O loaders through `object`, 32-bit x86, and decompiler options beyond the limit (DWARF types and the demangler came in phase 5).
3. **Confinement. Done on Linux:** the engine runs in a confined child process (`kraken-native-worker`) under the existing sidecar spawner. A crash or hang in C++ costs one request, not the daemon. A watchdog gives hard timeouts and cancellation, and restarts the worker. A restart re-opens the program, replaying the state directory's `native-state.json` (saved edits and the signatures the analysis job wrote), then replays the edits accepted since; without a state directory, signatures the analyzer filled in are lost on a restart.
4. **Mutation and the host. Done:** `Mutator` (renames, comments, function create/delete, types) applied from the edit log (see Mutation above), with the state directory instead of the .NET engine's replay of the log on open, in the worker and in-process; and `kraken-host` engine selection with Ghidra/native/auto per project recorded in `meta.json`: `project_create --engine`, `engine` in `config.toml`, `project_info` reporting the engine and why `auto` chose it, `kraken setup --native`.
5. **Licensing, rebuilt references, C++ names and DWARF. Done** (see above): the Ghidra decompiler and zlib license and notice texts in `THIRD-PARTY-NOTICES.md` and the release archive, with a staleness check; the reference index, exports and noreturn set rebuilt after structural edits; demangled C++ names with the mangled ones kept; DWARF types and prototypes.
6. **Windows:** build with MSVC or clang-cl (the `cc` crate already handles that; Ghidra's own build has the flags), then decide whether the native engine becomes the default.

## Consequences

- KRAKEN can load, analyze, list, disassemble and decompile ELF binaries, and answer xref, CFG, string, symbol and type queries, with no JVM and no Ghidra install. Decompiling is fast: the 375 functions of `cpp_shapes-O0` take under 0.4 s.
- Building the library takes about 40 s of parallel C++ compilation once per profile. CI without the cached sources builds the stub and skips the native tests.
- A decompiler crash or hang costs one request and a worker restart (re-opening the program; a second or more for static binaries), not the daemon. Decompiles are serialized per worker. In-process mode keeps the old limits: a crash takes the process with it, and a cancelled or overlong decompile stops at the next action break point.
- Structural edits rebuild the reference index, exports and noreturn set over the whole program; on a static glibc binary one edit takes about 0.4 s in a debug build. A changed noreturn mark does not re-walk the callers' bodies (discovery did that once), so code after a call that became noreturn stays in the caller.
- Without DWARF, local functions show inferred types (`int *param_1`) until a prototype is defined in the type store; library calls are typed from the prototype table (with the C library headers' parameter names, `__format`, as Ghidra shows them). With DWARF the type store holds the program's types under C identifiers, so the decompiler prints `vector_double__std__allocator_double___` where Ghidra prints `vector<double,_std::allocator<double>_>` (the listed signatures use Ghidra's spelling). DWARF variables (globals, locals) are not imported yet.
- Where the native engine and Ghidra disagree on the corpus, it is mostly by design or a Ghidra artifact: Ghidra gives imports addresses in a synthetic `EXTERNAL` block, makes no operand references in code its switch analysis reaches late, and leaves landing pads out of C++ bodies.
- Static binaries open slowly: about 10 s each in a debug build, almost all of it spent in the decompiler's switch recovery for glibc functions.

## Alternatives considered

- **Hand-written `extern "C"` instead of `cxx`.** Fewer dependencies, but more unsafe code on our side. `cxx` (MIT/Apache-2.0) checks both sides of the boundary and passes `cargo deny`.
- **Parsing `EmitMarkup` output.** That is what the Java side does. It needs an XML or packed decoder on the Rust side for something the emitter can record directly.
- **The `libsla` crate for lifting only.** No decompiler, and the decompiler needs Sleigh anyway.
- **Pure-Rust decompiler ports** (koute/ghidra-decompiler, rsleigh). Too young (see ADR 0001).
- **Copying rz-ghidra's glue.** LGPL, and its structure is tied to rizin's analysis model. We read it for orientation only.
- **The child process from day one.** It would mean debugging the glue and the transport at the same time. The trait boundary keeps the move cheap later.
