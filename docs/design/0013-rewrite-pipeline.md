# 0013. The rewrite pipeline

Status: Accepted
Date: 2026-10-16
Revised: 2026-10-18 (task R2: repair attempts, reused callees, stale units; task R3: whole programs; task R4: program-level repair, pointer graphs, doubles and callbacks, the GUI program view; task R5: real programs: the program image, floats, C++ names, unchecked functions, files)

## Context

KRAKEN's goal is a Rust rewrite of a binary. Decisions 2, 46 and 53 fixed the shape: two modes (faithful incremental, spec-then-reimplement), a generic versioned artifact linked to function anchors, and capability traits that let an emulator or a decompiler be replaced piece by piece. The rewrite spike (`spikes/rewrite-loop/NOTES.md`) proved the loop on four corpus functions: decompile through the registry, translate with a model, run the original machine code and the Rust side by side, record a versioned unit. It also showed what is hard: the translation is untrusted code that has to run, the original has to run somewhere, and "it passed" has to mean something.

This record turns the spike into the pipeline core of release 0.5 (task R1). It settles the questions the spike left open and says what is in the first cut and what is not.

## Decision

### Two modes, one record

A project rewrites function by function. Each `rewrite_function` call picks a mode, and both modes write the same unit record.

- **Incremental, test-verified (strangler).** The model gets the decompile of one function and its direct callees and writes a Rust function behind the original's `extern "C"` signature. The Rust function is checked against the original machine code. Accepted functions are exported as a library and an FFI shim that can stand in for the originals, so the program is replaced a function at a time and keeps running from the original binary for the rest.
- **Spec-then-reimplement.** First `rewrite_spec` has the model write a behavioural spec: Markdown with the headings Purpose, Inputs, Outputs, Side effects, Invariants and Open questions, every fact cited as `[@0xADDR]`. A citation must name a function entry or a hex literal in the evidence, or the reply is rejected. Then `rewrite_function` with `mode: spec` gives the model the spec and the required signature and no decompile, and checks the result with the same differential test. The spec is stored and can be read and corrected by a person (that is the human edit point of the mode). In this cut the spec is per function, plus one program-level spec for orientation. Module specs and whole-program reimplementation from specs come later; whole programs are rewritten in incremental mode (see "Rewriting a whole program").

The mode is recorded in the unit. Users pick the mode per call; there is no project-wide switch yet.

### The unit lifecycle

A function has a unit; a unit has append-only versions, one per translation. A version has a status:

```
planned -> translated -> verified -> accepted
                     \-> failed
```

- `planned`: the function is in the stored plan and nothing was translated.
- `translated`: Rust exists but there is no passing verdict (the oracle could not evaluate enough cases: `inconclusive`).
- `verified`: the differential test passed on every case that ran.
- `failed`: a case disagreed (the verdict carries the smallest counterexample), or the code was refused by the source lint, or did not compile.
- `accepted`: a user accepted a verified version.

A verdict decides the status of a new version: pass gives `verified`, fail and rejected give `failed`, inconclusive gives `translated`. Only a user moves `verified` to `accepted` (`rewrite_accept`). A function has at most one accepted version; accepting another version replaces it and the old one goes back to `verified`. A later translation does not unaccept a function, so an export is stable while people keep experimenting. Every transition is recorded as an event with its actor.

### Repair attempts

A translation that fails for a reason the model can act on gets another chance. `rewrite_function` runs a bounded loop (`max_attempts`, default 3, at most 8; 1 turns it off): ask for a translation, verify it, and if the new version is `failed` feed the evidence back and ask again. Three things count as repairable and each has its own feedback: `compile` (the compiler output, which `rustc` printed in the sandbox), `rejected` (the source lint's reason) and `counterexample` (the smallest disagreeing input, with what each side did). `inconclusive` and `translated` are not repaired, because the model cannot fix an oracle that could not run the original. A pass ends the loop.

The next request is the first request plus, per failed attempt, the attempt's code and the evidence, both inside `untrusted` blocks (the compiler output and the counterexample come from running model code against the binary, so they are data, like the decompile). A reply that cannot be parsed is an error on the first attempt, as before; on a later one it costs an attempt and the model is told what was wrong with its reply. The loop checks the job's cancel token between attempts.

Every attempt is stored as a version, so the history shows what was tried. A version made in a run carries a repair link (`unit_repairs`: attempt number, the version it answers, the kind of feedback), and its provenance task is `rewrite_function` for the first attempt and `rewrite_function/repair` for the others. The result of the job is the last attempt and says how many were made. The oracle is built once per run, on a dedicated thread, because it is not `Send` and is slow to build; each attempt is a job sent to it. Accepting stays a separate, human step: a repair never accepts anything.

### Reusing accepted callees

Before a translation, each program callee is looked up. When the callee has an accepted unit made from the callee's current decompile (same hash), and the callees that unit reuses in turn are still accepted at the version it was made with, the new translation does not translate it again. The prompt lists the callee by its original name, address and Rust prototype and tells the model to call it and not define it; a reply that defines it anyway is refused. The callee's decompile is left out of the prompt, which keeps prompts short on call-heavy code.

For the differential test the accepted code is compiled together with the new code: each reused callee, and what it needs in turn, in a private module (`__kr_callee_<addr>`, so helper types and functions cannot clash), then `use` lines for the ones the new code calls directly. That composed source is what the lint and the compiler see, and it is part of the test, not of the stored code: the unit keeps only the model's own code, and its callee list records each reused callee with the accepted unit and version it was tested against (`reused`). In the export a unit that reuses a callee gets `use super::u_<callee>::<callee>;` and the export refuses it when the callee is not exported, or is accepted at another version now, because the verdict was about the old callee; the message says to translate the function again. Spec mode does not reuse callees: its prompt contains the spec and nothing derived from the decompile. A callee that is not accepted, or is out of date, is translated inside the unit as before. A function never reuses itself.

### Stale units

A version is stale when the decompile of its function, or of a callee it was made from, is different now. Each version stores the decompile hash and the callee hashes it was made from. The store keeps the newest decompile hash it has seen per function (`observed_hashes`): storing a version records the hashes it was made from, `rewrite_function` records what it just read, and `rewrite_unit` decompiles the function and the callees of its versions and records those. `rewrite_status` reports `stale` per function from what has been recorded, without decompiling anything; `refresh: true` decompiles every function that has a unit, and the callees of the version that counts, first. The version that counts for a function is its accepted one, or else its newest. A stale unit keeps its status: stale is a flag next to it, not a lifecycle state, because the unit may still be right and only the user can say so. Translating the function again from the new decompile and accepting that version clears the flag. It does not block an export (the README of an export should list stale units; not done yet).

### Oracle kinds

Every verdict records the oracle that produced it (`kind`, emulator pin, binary, entry). Kinds:

| Kind | State | What it is |
|---|---|---|
| `icicle-emu/x86-64-sleigh` | implemented | The function runs in icicle-emu, a p-code interpreter fed with Ghidra's x86 SLEIGH spec, with the ELF mapped by hand and a few libc functions stubbed. Observed: result, buffers, stdout and stderr, writes to globals, how it ended. |
| `ghidra-pcode` | reserved | The same idea through Ghidra's `EmulatorHelper` in the sidecar. All Ghidra languages, a JVM round trip per call. Useful as a second opinion; it shares the SLEIGH semantics, so it would not catch a SLEIGH bug. |
| `native-process` | reserved | One function of the original run natively in the sandbox, for same-architecture hosts. The only function-level kind that catches emulator and SLEIGH bugs. (The whole program does run natively for the `process` kind below.) |
| `compile-only` | implemented | No oracle: the translation is linted and built, nothing is compared. Used for functions the oracle cannot compare (a pointer result) and when a program rewrite was asked not to run the function-level test. The verdict is always `inconclusive`. |
| `process` | implemented (`rewrite_program`) | Whole-program oracle: the original binary and the generated Rust crate are run in the sandbox on the same arguments and standard input; exit status, stdout and stderr are compared. It sees what the emulator cannot (the real libc, the real loader) and what a function test cannot (the program as a whole). |

All of them sit behind one trait once a second kind exists (`Emulator` in `kraken-engine`, decision 46). Until then the oracle is the concrete `FunctionOracle` in `kraken-rewrite`, and the trait is extracted when the second implementation needs it. Inputs are generated, not harvested: edge and random values for integers, random bytes in fixed-size buffers for pointers, curated generators for known targets (the corpus). Harvesting real arguments by running the program is planned.

A verdict is evidence, not proof: "N seeded cases agreed". Coverage of the original is not measured yet.

### The emulator dependency

icicle-emu stays a git dependency pinned by commit (`crates/kraken-rewrite/Cargo.toml`, `deny.toml` `allow-git`), used through `icicle-cpu`, `icicle-vm` and `pcode`. It is MIT OR Apache-2.0, executes SLEIGH p-code like Ghidra does, and has no releases. Unicorn is GPL-2.0-only and cannot be combined into a GPL-3.0-or-later work. The risk is a single research-grade upstream, which the pin contains. If upstream stalls, the options are a vendored fork or the `ghidra-pcode` kind as the primary oracle; both fit behind the same trait. This is revisited before the 0.5 release.

### Sandboxing generated code

The translation is model-written code and it is built and run on the user's machine. It is untrusted. Rules:

- It runs only in a confined child process. Today that means Linux with Landlock ABI 4 or newer (kernel 6.7) plus network isolation: a user and network namespace when the host allows one, otherwise a seccomp filter that refuses `socket()` outside `AF_UNIX` (the filter is installed in both cases, also refusing `io_uring_setup`). The build (`rustc`, or `cargo` for an export; the real toolchain binaries from `rustc --print sysroot`, never a rustup proxy) can read only the toolchain sysroot, `/usr`, `/lib*`, `/etc/ld.so.cache` and `/proc/self`, and write only its scratch directory, which lives under a private `0700` directory (`$XDG_RUNTIME_DIR/kraken-rewrite`, never a shared `/tmp`, with no cargo config in any ancestor) with an explicit `CARGO_HOME`; it also runs under `RLIMIT_AS`, `RLIMIT_CPU` and a 120 s (cargo: 600 s) wall-clock limit. `$HOME`, `~/.ssh` and the daemon token are unreadable even to `include_str!`. Each test case runs in a tighter child: system libraries and `/proc/self` read-only, write only to its scratch directory, no sockets at all, no `fork`/`clone` (seccomp), `RLIMIT_AS` 2 GiB, `RLIMIT_CPU` 30 s, `RLIMIT_FSIZE` 64 MiB, no core files, a 10 s wall-clock kill, `PR_SET_PDEATHSIG`. Every child leads its own process group, and a timeout kills the group; reader threads are joined with a deadline so a descendant that escaped cannot hang the daemon. The source lint is a `syn` allowlist (safe computing subset: no `extern` blocks, no `mod x;`, a short list of attributes and macros, no file, network, process, environment or thread APIs) and is defence in depth; tests prove that the confinement holds without it.
- A source lint runs before any build and refuses `include!` and friends, `env!`, inline assembly, `#[link`, crate-level attributes, `extern crate`, `libc::`, `std::fs`, `std::net`, `std::env`, `std::process::Command` and OS-specific modules. It is defence in depth; the sandbox is the boundary.
- It fails closed. A host that cannot enforce this (Landlock ABI 4 and a network barrier) does not run generated code at all: `rewrite_function` and the building part of `rewrite_export` answer `unsupported`. There is no flag to run unconfined from a command. macOS and Windows therefore cannot rewrite until they have their own confinement (App Sandbox, Job objects with restricted tokens). The commands are still defined there and say why they refuse.
- Permission classes follow from this. `rewrite_function` is `mutating`, not `dangerous`, because the sandbox is enforced or the command does not run. It only adds artifacts to `rewrite.sqlite`; it never edits the program, so agents may run it. `rewrite_export` is `mutating` when it writes inside the project directory and asks for approval, exactly like a `dangerous` command, when the target is outside it (the approval request names the directory; a `..` in the path is refused outright). `rewrite_accept` is for users only; agents get `rejected_human_priority`.
- Not done yet: a network namespace and a seccomp filter for the generated code, which should come from one `kraken-sandbox` crate shared with the Ghidra sidecar (ADR 0007), the inference backends and the ACP agents.
- Model calls send decompiled code to the configured provider (`[rewrite]`, else `[provider]`). A cloud provider or a terminal agent's service sees the code of the functions being rewritten; a local model does not. This is the same as for the assistant (ADR 0008), and the commands' documentation says it. A terminal agent used for rewriting gets no KRAKEN tools, runs in an empty scratch directory and has every permission request for its own tools denied (see "Model calls run on the assistant's backends").

### Model calls run on the assistant's backends

Every model call of the pipeline (a translation, a repair attempt, a spec, the reimplementation from a spec, a program-level repair) goes through `kraken_assist::AssistBackend`, the same trait the assistant runs on (ADR 0008, decision 94), not directly through a chat provider. `RewriteService` takes a `BackendSource`; the standard one reads `config.toml` on each call: the optional `[rewrite]` table when there is one, else `[provider]`. Both have the keys of a provider table, so either can be a model API (`ApiBackend`) or `kind = "terminal_agent"` (`AcpBackend`: Claude Code, Codex, Gemini CLI, any ACP agent).

The trait gains one method for this, `complete_text(ChatRequest, cancel) -> TextReply`: one text-only request, no tools. The API backend calls the provider as before (the request is unchanged, so the checked-in cassettes still match). The terminal agent starts a fresh session per call, with these differences from an assistant task:

- It runs in an empty scratch directory, not the project, and gets no KRAKEN MCP server: everything it needs is in the prompt, so it has no tool to call.
- The prompt is a fixed preamble (a text-only request; do not use tools, files or commands; KRAKEN builds and checks the answer itself) followed by the same system text and user message a model gets. The agent returns the translation in the existing result format and KRAKEN parses it like any other reply.
- Permission is `DenyAll`: a request to use the agent's own tools (write a file, run the build) is answered "reject" without asking anyone, counted, and reported as a note. The ACP client already declines file reads and writes the agent asks of KRAKEN. Only KRAKEN builds and tests, in the sandbox above; the agent never does.
- A refusal, a failed start, a cancelled job or an empty reply are errors of the model call (`RewriteError::Provider`); an unusable reply is handled as before (a failure of the attempt, then the repair loop).

A unit records the provider id and model of whoever answered (for an agent, the agent id and the model it reported), so provenance, specs and the export manifest are unchanged. The agent can still use whatever its own settings allow without asking permission; that is the same limit as for the assistant, and the empty scratch directory is what keeps the project out of reach.

Tests: `kraken-rewrite/tests/acp_backend.rs` runs `rewrite_function` (also with a repair attempt and in spec mode) and `rewrite_program` with the fake ACP agent answering with the reference translations, and checks that an agent that asks to write a file and run `cargo build` is refused both; `kraken-assist/tests/backends.rs` covers the text request on both backends and the `[rewrite]` precedence. The cassette tests are unchanged apart from wrapping their provider in `ApiBackend`.

### Where the pieces live

- `kraken-registry` defines the six commands, their arguments and results, and the `RewriteBackend` trait. A `Session` carries an optional backend (`Session::with_rewrite`), as it carries an `EngineFactory`. Without one the commands answer `unsupported`.
- `kraken-rewrite` implements `RewriteBackend` (`RewriteService`) and owns everything else: the oracle, the tasks, the sandbox, the store, the planner and the export. `krakend` and the `kraken` CLI attach it to the sessions they own. The in-process GUI session does not yet; it reaches the pipeline through the daemon.

The other directions are worse. If the registry depended on `kraken-rewrite`, the registry would link the emulator, the sandbox and a second SQLite schema, and there would be a dependency cycle, since the pipeline reads the program through registry commands. If `kraken-rewrite` registered its commands into a `Registry`, every place that builds `Registry::standard()` (the CLI's command tree, the MCP tool list, the generated reference, the GUI's palette, the daemon contract tests) would have to remember to add them, and a surface that forgot would silently lack the commands. With the commands in the registry they appear everywhere, in the same order, with the same schemas, and the implementation is injected where it is needed.

### Commands

| Command | Kind | Permission | Does |
|---|---|---|---|
| `rewrite_plan` | query | safe | Orders the functions callees first (strongly connected components of the call graph, recursive groups together), leaves out import thunks and compiler glue, flags what the test cannot cover. `scope: all` stores the plan and pages through it; `scope: function` returns one function with the callees it needs. |
| `rewrite_status` | query | safe | Counts per status and one row per function. |
| `rewrite_function` | job | mutating | Decompile, translate with the configured provider, build and test in the sandbox, store a new version. |
| `rewrite_accept` | mutation | mutating, users only | `verified` to `accepted`. |
| `rewrite_spec` | job | mutating | Write and store a cited spec, for one function or the program. |
| `rewrite_export` | job | mutating (approval outside the project) | Write a Cargo workspace from accepted units and build it in the sandbox. |
| `rewrite_program` | job | mutating (approval for agents, and outside the project) | Rewrite a whole program: plan, translate every function bottom-up, write and build a standalone Rust binary crate, run it against the original. |
| `rewrite_program_status` | query | safe | The stored program rewrites: functions, crate location, the program verdict with per-case differences. |

The plan flags: `needs_stubs` (a library call the oracle does not model, directly or through a callee; the test would be inconclusive), `uses_globals` (a data reference into writable program data; the globals are not inputs of the test), `uses_syscalls` (a call to `syscall`; an inline `syscall` instruction is not detected) and `recursive`. The oracle's stub list is in `kraken_rewrite::oracle::STUBBED_IMPORTS`; the planner uses the same list, so the flag and the oracle agree by construction. References to the program's own copies of `stdout` and `stderr` do not count as globals, because the oracle models them.

The CLI and MCP get all of this from the registry. `kraken` prints `rewrite-plan`, `rewrite-status` and the result of `rewrite-function` as tables and short text; every command has `--json`. The assistant does not get the commands that start model calls or builds (`rewrite_function`, `rewrite_spec`, `rewrite_export`, `rewrite_accept`); it may read the plan and the status.

### Rewriting a whole program

`rewrite_program` (task R3) is the end goal of the pipeline: a Rust program that behaves like the binary. It is a mode of the same machinery, not a second one: the function-level loop (translate, check, repair, store) is the one `rewrite_function` runs, and the program command adds the order, the assembly and the program-level test.

**Order and context.** The plan (`scope: all`) orders the functions callees first, recursive groups together. Only the functions the entry point reaches by direct calls are translated; the others are rows with check `skipped` (loader and compiler glue in a binary without names, dead code, and the libc inside a static binary: `static_strops` has 68 functions in the plan and 8 are the program). Functions reached only through function pointers are not found yet. Each function is translated with what is already known about its callees: a callee that has a usable translation (see below) is *called* as Rust, exactly as with accepted callees, and a callee that has none is translated inline, together with everything it calls in turn that has no translation either. That makes a recursive group work without a special case: the first member of `parse_atom`/`parse_term`/`parse_expr` is translated with the other two inside it, and the later members call the first one. A callee whose decompile changed since its translation was made is not called (the hash check of accepted callees applies). Duplicated helper code inside units is the price; every unit is self-sufficient and checkable alone.

**What counts as usable.** In a program run a translation is usable when it did not fail (`verified`, `translated` or `accepted`), not only when it was accepted: accepting is a person's decision and a program rewrite must not wait for one per function. `accept_verified: true` (users only; the command refuses it from an agent) additionally accepts the functions whose own test passed, and an accepted unit made from the current decompile with its callees unchanged is taken from the store instead of being translated again. A function without a usable translation is a row with status `failed` and the reason; the run goes on, because its callers may carry its code inline.

**The function-level check in a program run.** It is evidence about one function and is labelled as such on every row (`check`): `differential` (the emulation oracle, as for `rewrite_function`), `compile_only` (built and linted, nothing compared: the oracle cannot compare a pointer result, or the call passed `verify_functions: false`, which also makes the run need no Ghidra install). Functions of the switch_vm helpers get curated inputs (`targets::curated`); functions whose arguments hold pointers (the stripped_calc parser) cannot be tested with random bytes, and the test now says so: when the original faults on at least 90% of the cases the verdict is `inconclusive` instead of a vacuous `pass` (the two sides agree about crashing). Signatures stay within the oracle's ABI (integers and pointers, at most six parameters); a pointer result is allowed here and only compiled. Since task R5 a row can also be `unchecked`: the translation is in the crate although its own test failed or could not run (see "Real programs"); `float`s are in the ABI and unsized types are read as 64-bit registers; varargs functions of the program are still a `failed` row.

**The crate.** The units that the entry point needs, found through the callees each chosen translation calls, become a standalone binary crate: `src/main.rs` builds `argc`, `argv` and `envp` as the C runtime does and calls the translated `main`; `src/u_<name>.rs` is one module per function (the model's code with its symbol attributes removed, `use` lines for the translations it calls); `src/rt.rs` is the runtime shim; `Cargo.toml` has no dependencies and its own `[workspace]`; `kraken-program.json` is the manifest and the marker that lets a later run overwrite the directory (any other non-empty directory is refused). The crate is written to `rewrite-program` in the project directory unless `dir` says otherwise, with approval outside the project. It is the model's code: it is built only in the sandbox, and the README says to read it before trusting it.

**The runtime shim.** `kraken_rewrite::rt` (embedded as `RT_SOURCE`) maps the libc calls the corpus programs make onto Rust `std`: `printf`/`eprintf` with C format semantics (flags, width, precision, `*`, length modifiers, integer, string, character, pointer and common floating-point conversions) over typed variadic arguments, `puts` and friends, `exit`, the `string.h` functions, C-locale `ctype`, `malloc`/`calloc`/`realloc`/`free` (16-byte aligned, with a size header), `strtol`/`atoi`. It is ordinary tested Rust, it passes the translation lint, and in a program run it is in scope for every translation as the module `rt` (the prompt lists it), both in the crate and in the function-level test of a translation, so a unit that uses it is tested the way it will run. Translations may also use `print!`/`eprint!`/`std::process::exit` where the decompile prints a constant or exits. Stdout goes through Rust's line-buffered stdout where libc buffers a pipe fully; since the program test captures stdout and stderr separately, only their interleaving could show it.

**The program-level test.** The original binary and the built crate are run on the same cases, each run in its own private directory with a copy of the executable, under the runner confinement (read-only system files, no network, no `fork`, memory, CPU and output limits, scrubbed environment, `argv[0]` fixed to `prog`). Exit status (code, signal or timeout), stdout and stderr are compared byte for byte, and the first differing byte of each stream is reported with its context. The cases are: a baseline run (no arguments, empty input); cases derived from the program's source when it is a corpus program (`corpus/src/<name>.c`: its string literals, as arguments and as input, plus awkward shapes when the source reads `argv` or `stdin`); seeded generated cases (`generated_cases`, default 8); and cases the caller gives (`inputs`). The corpus programs read neither argv nor stdin, so for them most cases check that the rewrite ignores its input as the original does, and the baseline run is where the program's own behaviour is compared. The verdict (`pass`, `fail`, `incomplete`, `inconclusive`) and every case are stored in `rewrite.sqlite` (`program_runs`) and read back with `rewrite_program_status`. `incomplete` means no runnable rewrite exists (a function the program needs has no usable translation, or the crate does not build); the reason is the compiler output or the name of the function. A failed program verdict is not repaired automatically yet: the differences go to a person.

**Status on the corpus** (all `-O0`, rewritten from hand-checked reference translations through cassettes; see `crates/kraken-rewrite/tests/program.rs`): `stripped_calc` (with symbols and stripped, the stripped one entered through the entry stub), `switch_vm`, `static_strops` and, since task R4, `pie_list` are rewritten end to end and match the original on every case. `pie_list` needs function pointers (its comparison functions are reached only through a table, its visitors are passed by address), `double`s (a parameter, a field, `printf("%.1f")`) and linked nodes; see "Pointer graphs, doubles and callbacks". `cpp_shapes` is C++ (methods with `this`, vtables, libstdc++ instantiations) and is far outside the ABI; the `-O2` builds have not been tried beyond planning. The reference translations are written by hand: a model has not yet been run against `pie_list`.

**Safety.** This is the first place where the binary under analysis runs natively. It runs confined as above, and the command is refused on hosts that cannot confine. A call made for a person (an agent, MCP) asks for approval first, with a summary that says the original will be executed. The GUI asks too (task R4): its Run button goes through the approval dialog that every dangerous command uses, because a click on a button that runs a binary deserves the same question as any other dangerous step; no model call and no run happen when the answer is no. A person typing `kraken rewrite-program` at the CLI is not asked, because they started the command. A confined native run is not a virtual machine: the kernel is shared, so analysing malware should still happen in a VM (docs/security.md says so). `build: false` writes the crate and runs nothing.

### Program-level repair

A failed program verdict is not the end (task R4). With `repair_rounds` (default 2, at most 4, 0 off) the job feeds the first differing case back through the repair loop that `rewrite_function` already has. One round:

1. **Where it shows.** The first difference is a byte of stdout or stderr that differs (or output that is missing), or an exit status. The crate is rebuilt with optimisation off and line tables on, and the rewritten program is run again on that case with `KRAKEN_TRACE_AT=out:<byte>` (or `err:<byte>`, `exit`). The runtime shim, which writes every byte of output and does `exit`, prints the call stack at that moment to stderr. The generated `main` arms this from the environment; unset, nothing happens.
2. **Who to blame.** The functions on that stack, then their callees, are suspects, ranked by how much they were trusted: first the ones that were only compiled or whose function-level test could not tell (the stack functions innermost first, then callees nearest first), then the ones that passed the differential test against the original, which stands in for bisecting with the accepted original (the original is only ever run as a whole, natively, so it cannot be traced; a function-level pass is the evidence that a function agreed with its original on its own inputs). Output is often printed by a caller of the function that computed it, and that function has returned by then, so callees count. The first three suspects are the round (two before task R5); a function an earlier round already translated again comes after those not tried yet, so later rounds move down the list. This is a heuristic (`kraken_rewrite::blame` documents it and tests it), and it is bounded: a wrong guess costs a round, not correctness, because the verdict is recomputed.
3. **Feed back.** Each suspect is translated again through the normal loop (at most 2 attempts), seeded with a repair round of kind `program`: its own previous code and a text with the case (arguments, input), both programs' output, exit status and the differences, the stack, and why this function is suspected. It reaches the provider inside an untrusted block, as compiler output and counterexamples do. A new translation that fails its own function-level check is not used. A suspect whose reply cannot be used costs nothing else.
4. **Rebuild and compare.** If any function changed the crate is written again (callers keep calling the newer version of a repaired callee: the version check of the export is relaxed for program crates, the symbol still has to match), built, and every case is run again. The loop ends when the verdict is no longer `fail`, when a round changes nothing, or when the rounds are used up. Every suspect of every round is in `repairs` with its case, trace, reason, outcome (`replaced`, `kept`, `no_reply`) and the verdict after the round.

### Pointer graphs, doubles and callbacks

The call description of the function-level test grew three things (task R4), all shared by the emulation oracle and the native runner:

- **Pointer graphs** (`Arg::Graph`). Several objects that point to each other: each object is its own allocation, and the links are written as addresses before the call. Both sides place object `n` at the same address (`abi::place_object`: its own page-aligned mapping, the data against the end of it and 8-byte aligned, nothing mapped around it; the runner uses `mmap` with `MAP_FIXED_NOREPLACE`), so a pointer stored in an object has the same value on both sides, buffers compare byte for byte including the pointers, and a read or write outside an object faults on both sides (before, the runner read zeros there and the emulator faulted). Generators build lists (`SlotGen::Chain`, with the count field set), texts that a struct points to, and unknown structs (`ParamGen::Mixed`). With them the parser functions of `stripped_calc` pass the differential test against the original for real, and a parser that forgets to set `err` is caught, which random bytes could never reach.
- **`double`** (`Param::Double`, `Ret::Double`) in `xmm0` to `xmm7`, numbered apart from the integer registers, compared by bit pattern; in memory they are plain bytes. The emulator's `printf` stub does not format floating point, so a function that prints a `double` is `inconclusive` at function level (the program-level test still compares the output; the runtime shim formats `%f`, `%e` and `%g`).
- **Function pointers** (`Param::FnPtr`). The test passes one of two host callbacks (ascending or descending): they take up to two pointer-sized arguments, answer with the difference of the first 32 bits the two pointers point to (or 0), and record every call as text (`cb0(o1+0=3,o2+0=7)=fffffffffffffffc`: which object each argument points into, and what is there). Both sides implement them the same way (a breakpoint stub in the emulator, an `extern "C"` function in the runner) and the recorded calls are compared, so a sort that calls its comparator with the arguments swapped, or does not call it, is caught. Callbacks that need more than that (doubles, three arguments) are not modelled.

In a program run, functions that are only reached through a function pointer (the comparators of `pie_list`, in a table in `.data.rel.ro`) are found from the data references: a function whose address a function stores, or whose entry sits in a data table within 128 bytes after an address that function refers to (in a data block, not the unwind tables beside it), is a callee of that function, so it is translated first and the prompt says that the address is taken, not called.

### Real programs (task R5)

The first whole-program runs on a real C++ program (the owner's audio simulator `sim04`, 68 planned functions) ended `incomplete`: 38 translated, 9 verified, `main` blocked. Every cause was a gap of this pipeline, not of the model. Task R5 closed them; the corpus programs are rewritten as before (their cassettes were re-recorded for the longer prompts).

- **The program image.** Real programs keep their state in globals, and every translated function used to be its own island: a global written by one function was invisible to the next, and the function-level test reported every write to a global as a difference ("the original writes N global location(s), which a translation cannot reproduce"). Now the original's `PT_LOAD` segments (file contents, zeroed `.bss`) are embedded in the crate (`src/image.bin`, `src/image.rs`, `kraken_rewrite::image`) and installed once before `main`, relocated as the loader would: `R_X86_64_RELATIVE` pointers point into the image, the program's copies of `stdin`/`stdout`/`stderr` hold the shim's streams, and pointers to functions that have a translation point at the Rust function (so vtables and callback tables call the translations). Translations reach program data only through `rt::g(address)` with the addresses the decompile shows; the prompt lists the named objects a function refers to (ELF symbols, demangled: `loop()::tick`) and forbids `static mut` for program state. The function-level runner installs the same image at the address where the emulator has the same bytes (the oracle's load base), so pointers stored in the data have the same values on both sides, and it reports the writes to the compared ranges exactly as the oracle does: writes to globals are now compared, not refused. The image is limited to 64 MiB.
- **Signatures.** `float` parameters and results (`Param::Float`, `Ret::Float`, the low 32 bits of an SSE register, numbered with the `double`s) in the ABI, the oracle, the runner, the export and the generated `main`. The name of a function is found in its signature by the name the engine shows, so C++ names parse (`~_Vector_base`, `operator()`, `{lambda(unsigned_short)#1} * this`, template instantiations). A program run reads a type the signature does not size (a struct by value, a class Ghidra could not size, `Button tap(Button * this)`) as a 64-bit register and says so in the prompt; the program-level test judges the guess. Rust names are unique per program: a method is prefixed with its class (`Button_begin`), a name that is not an identifier is made one, a name still shared gets its address (`begin_107d90`). `main` gets `argv` by position even when the decompiler typed it as `long`.
- **The function-level check is evidence, not a gate.** A translation that builds but fails its own test, or that the test cannot run (inputs that do not reach the logic: a C++ `this`; imports the emulator does not model), is used in the crate with check `unchecked`; the result counts `verified` and `unchecked`. Of the attempts of one function the newest that passed or could not be compared is used, else the newest that builds. Program-level repair still decides with the blame ranking; a new translation that builds is used unless it fails its own test where the old one passed. With callees always translated first, the inline limit was raised from 12 to 24 callees, and a program translation may answer with up to 16384 tokens.
- **Reachability.** Besides direct calls and function pointers handed on, a function whose address is stored in a table of the data (a vtable, a dispatch table) joins the program when a reached function refers to the table (the same ELF data object, or within 512 bytes when there is no symbol). Static constructors in `.init_array` named `_GLOBAL__sub_I_*` are roots and run before `main` in `.init_array` order.
- **The runtime shim** grew to what ordinary C and C++ programs call: stdio streams with real files (`fopen`, `fwrite`, `fread`, `fputs`, `fputc`, `fgets`, `fprintf`, `fseek`, `perror`, `strerror`, `errno`), math with the C library's own results (`sinf`, `powf`, `log2f`, `lroundf`, `sqrt`, ...), `strtod`/`strtof` (correctly rounded, hex floats, `inf`/`nan`), `strtoul`, `strspn` and friends, `qsort` (stable, as glibc's merge sort) and `bsearch`, glibc's `rand` sequence, `atexit`/`__cxa_atexit`, and the C++ basics: `operator new`/`delete`, uncaught `std::length_error` and friends ending the program with libstdc++'s message and `SIGABRT`, `__cxa_guard_*`, `__cxa_pure_virtual`, `_Unwind_Resume`. The shim is KRAKEN's code: it is compiled in front of a translation without the translation lint (the lint still refuses file APIs in model code); the sandbox confines both.
- **Files are compared.** Each program-level run reports the files it left in its working directory (size, SHA-256, a hash per 4 KiB block, the first bytes); a missing, extra or different file is a difference, and the trace can stop at the write that covers the first differing block (`KRAKEN_TRACE_AT=file:<byte>:<name>`).
- **The emulator** models more: `fputc`/`fputs`/`fwrite` to the standard streams, `strspn`/`strcspn`, `malloc`/`calloc`/`operator new` from a bump heap (`free` of the function's own memory does nothing; freeing an object the test passed in is unsupported, since the native side cannot reproduce it), the math functions, `std::__throw_length_error`, and a thread block behind `fs:` with a stack canary, so functions built with the stack protector run. A function without parameters is called once instead of 200 times.
- **The export** carries the shim (`<lib>/src/rt.rs`) and an `extern "C" kraken_attach_image(at, low, len)` that tells functions using globals where the original program's data is when they run inside it. An accepted function that calls one that is not accepted no longer refuses the export: the unaccepted callee is declared by the symbol the program has at its address (mangled for C++) and called in the original (`calls_original` in `manifest.json`, a table in the README); a callee without a symbol stops the program with a message when called.

What was measured with the configured terminal agent (Claude Code) on the owner's programs is in "Status on real programs" below.

### Persistence

Rewrite artifacts live in `<project>/rewrite.sqlite`, a file owned by `kraken-rewrite` with its own versioned migrations, not in `project.kraken.sqlite`. The project database is the edit log (ADR 0002) and `kraken-model` changes on its own schedule; the rewrite schema should not be coupled to it, and a rewrite database can be deleted and rebuilt without touching annotations. Decision 46 asked for a generic versioned `artifact` entity with typed links. This cut stores the rewrite artifacts as ordinary tables with the same content and keys (function anchor = program hash plus entry address); the generic table can be introduced in the project database later and fed from these tables by a copy, since versions are immutable.

Tables: `units` (one row per function: status, newest and accepted version), `unit_versions` (code and hashes, ABI, provenance with provider, model and prompt hash, oracle, decompile and callee hashes with the reused unit where there is one, spec id), `unit_repairs` (attempt number and the failed version a repair answers), `observed_hashes` (the newest decompile hash seen per function, for stale checks), `test_cases` (the oracle's expected results, capped at 256 per version), `verdicts` (verdict, counts, seed, sandbox label, counterexamples), `unit_events` (status transitions with the actor), `specs`, the stored plan (`plan_meta`, `plan_entries`), and `program_runs` (one row per `rewrite_program` run: the verdict summary and the whole result as JSON, including the per-case evidence). Migrations are numbered, applied in one transaction, recorded in `schema_version`, and a database from a newer build is refused. A test migrates a database written by migration 1 and checks the data.

### Limits

What the first cut cannot do, so nobody is surprised:

- Calls out: only the stubbed libc functions exist (`oracle::STUBBED_IMPORTS`: output to the standard streams, string and memory basics, a bump `malloc`, the math functions). Any other import ends the case as unsupported, and a function whose cases are mostly unsupported gets `inconclusive` (in a program run: `unchecked`). Files and syscalls are not modelled by the emulator; the program-level test runs the real ones.
- Signatures: at most six integer-class parameters (integers, pointers, function pointers) and eight `double`s or `float`s, an integer, `double`, `float` or void result. No structure by value, varargs or pointer results for a single function (a program rewrite accepts a pointer result but only compiles it, and reads an unsized type as a 64-bit register). `rewrite_function` explains which one and stops before any model call. The ABI is read from the signature KRAKEN shows; overriding it (`set_function_abi`) is not there yet. A function-pointer parameter is recognised from the C syntax, Ghidra's `code *` and `_func_...` types, and typedef names ending in `_fn`, `_func`, `_cb`, `_callback`, `_proc` or `_handler`.
- Pointers: a pointer parameter is a flat buffer or a pointer graph. Generic inputs are half 64-byte buffers of random bytes (for string and memory functions) and half small graphs of a 32-byte struct whose words are null, small numbers, text pointers or pointers to a second struct; curated inputs (`targets.rs`) build the exact layouts of the corpus structs. Pointers to memory the function allocates, to the stack or to globals are not compared (addresses differ), and `free` of an input object cannot be modelled, so a function that frees what the test gave it comes out `inconclusive`.
- Globals are flagged by the plan. In a program run they live in the program image and writes to them are compared at function level; their initial values are always the program's initial data, so a function that depends on state set up by other functions is tested from the wrong state and usually ends `unchecked`.
- Translation unit: a function with up to six of its direct program callees (their decompile as context). Callees that are not accepted yet are translated into the same unit, so a helper can exist in several units; accepted ones are called (see above). Translating a recursive group as one unit is a follow-up. The repair loop is bounded and only reacts to failures it can show the model; it does not search for a better prompt, and a model that repeats the same mistake uses up the attempts.
- Cost: one model call per attempt, so up to `max_attempts` (default 3) per function in incremental mode (one more when the spec is new in spec mode; the repair loop runs on the reimplementation, not on the spec), `max_tokens` 4096, temperature 0.1. A spec is reused while the decompile of the function and its callees is unchanged. Whole-program specs read at most 100 functions (30 by default), each cut to 6000 bytes. Token budgets per program and a response cache keyed by prompt fingerprint are not there; the cassette fingerprint is the ready-made key.
- Time: 10 s per case, 600 s for an export build, 2000 test cases at most, 2000 functions in a new plan by default (20000 at most).
- Only x86-64 ELF is run by the oracle. The plan and the specs work on any program the engine can load.
- Programs: only incremental mode, only x86-64 ELF, only programs whose functions fit the ABI above. A recursive group is translated inside its first member, so its code exists several times. The program-level test covers the inputs tried: the corpus programs read no arguments or input, so their program verdict is mostly the baseline run. Programs that read files, the environment or the clock, or that fork or use threads, are not covered (the runner forbids `fork`; the environment is empty). Program-level repair is bounded (2 rounds by default, 4 at most) and a ranking, not a proof (see below). Functions reached only through a function pointer join the plan when the program takes their address in code or in a table next to data the code uses; an address computed at run time is not seen. Stripped binaries work when `main` can be found (the decompile of the entry stub names it) or `entry` is passed.
- Emulator fidelity comes from SLEIGH. A bug there is invisible to `icicle-emu` and `ghidra-pcode`; `native-process` is the answer.

### What "done" means for a rewritten program

Three levels, from small to large.

1. **A function is done** when a user accepted a version that passed the differential test on every case that ran, with no counterexample and not mostly `skipped`. Its record says which model wrote it, which cases ran, which oracle checked it and in which sandbox.
2. **A program is rewritten** when every function in the plan is either accepted or deliberately left to the original with a reason (a waiver; not in this cut), no accepted function carries an unexplained `needs_stubs`, `uses_globals` or `uses_syscalls` flag, and the export builds in the sandbox with a symbol table that matches the accepted units. `rewrite_status` shows the counts; the README of the export shows the coverage.
3. **The original is retired** when the program as a whole behaves the same: the original's own test inputs, run through a build that drops the originals, give the same output and status as the original. `rewrite_program` automates this for exit status, stdout and stderr on the inputs it is given (the `process` oracle); it does not check files written, and the inputs are the ones the caller has: level 3 still needs the program's own regression inputs. The strangler export (`rewrite_export`) is not covered by it.

Differential testing is evidence. "Done" at every level means "no known difference on what was tested", and the reports say how much was tested.

### The export

`rewrite_export` writes a workspace with a library crate holding the accepted units, one module per function with the model's symbol attributes removed, and an FFI shim crate (`cdylib` and `staticlib`) exposing one `extern "C"` function per unit with the original name and signature, plus a C header, `manifest.json` (symbol, original address, unit, version, cases, provider) and a README. The README states the coverage, what the tests do not control, and three ways to link the shim in place of the originals: rebuilding from source, symbol interposition for dynamically exported functions, and patching the binary (not provided). By default the workspace is built in the sandbox and its dynamic symbol table is compared with the accepted units; any difference fails the export and leaves the files for inspection. The target directory must be absent, empty, or an earlier export (marked by its manifest); anything else is refused.

### The security advisory for `ruzstd`

`cargo deny` reports RUSTSEC-2026-0344, an advisory against the `ruzstd` zstd decoder, for the dependency graph through `icicle-cpu`, which depends on `addr2line`, which pulls in `object` with zstd support. icicle-cpu has no feature that drops this, and a `[patch]` would need the workspace manifest, so the dependency stays and the advisory stays ignored in `deny.toml` with this reason. The code is unreachable from KRAKEN. The decoder runs only when `addr2line::Context::from_dwarf` reads compressed DWARF sections of a program image, and the only caller in icicle is `icicle_cpu::debug_info::DebugInfo::add_file`, used by its PE loader and by `icicle-linux`. The oracle maps `PT_LOAD` segments itself and reads symbols and relocations with `object`'s ELF reader; it calls neither. A test (`crates/kraken-rewrite/tests/no_debug_info.rs`) fails if `kraken-rewrite` source starts to name any of these entry points, or adds an icicle crate beyond the three it uses. The ignore is removed when `object` in icicle moves to `ruzstd` 0.9.1 or later.

### The GUI program view

The Rewrite tab has two sections (task R4): the per-function one and "Whole program". The program view reads `rewrite_program_status` and shows the stored runs (a run picker), the verdict with a one-line reading, the entry point, how many functions were never compared with the original on their own, the crate folder with copy and open buttons and a built chip, the function table (translation status, how it was checked, function-level verdict, tries, in the crate; a click shows its note and the callees it calls), the repair rounds, and the cases. A case shows its command line and three comparisons: exit status, standard output and standard error, the two streams as a line diff with `-` for lines only the original printed and `+` for lines only the rewrite printed (the marks, not only the colour, carry the meaning). Cases that agreed are loaded on request. The Run button starts the job through the daemon, whose approval question (the original program will be run) is answered in the approval dialog; a no is not an error. `kraken-gui --demo --scene rewrite-program --screenshot out.png` renders a scripted two-run history.

## Consequences

- The loop of the spike is a product feature: plan, translate or reimplement, verify, record, accept, export, from the CLI, MCP and (through the daemon) the GUI, with one implementation.
- Generated code never runs outside the sandbox, and hosts without one cannot rewrite. That is a hard limit on macOS and Windows until they have confinement.
- The rewrite state is separate from annotations, so it can be inspected, copied or thrown away on its own, and a schema change in one does not force one in the other.
- The icicle dependency adds a long build and about fifty packages to `krakend` and `kraken`, and one advisory ignore with a documented reason.
- A passing unit is only as good as its inputs. Struct-heavy and stateful functions need curated or harvested inputs before their verdicts mean much; the plan flags make the known gaps visible.

## Alternatives considered

- **Rewriting only against `ChatProvider`.** The first version did, which left Claude Code and the other terminal agents out of the pipeline (`ConfigProvider` refused a `terminal_agent` table). Running on `AssistBackend` costs one trait method and keeps a single configuration.
- **Letting the agent use KRAKEN's tools or build the code itself.** A terminal agent could read the program through MCP and iterate with its own compiler. Refused: the verdict must come from KRAKEN's oracle and sandbox, the prompts must be the same on every backend so results are comparable, and an agent that builds on its own is outside the confinement.
- **One long agent session for a program.** Cheaper to start, but the context would grow with every function and a poisoned earlier reply could steer later ones. A fresh session per call keeps requests independent, as they are for a model API; the start-up cost is paid per call.

- **One generic `artifact` table in the project database now.** Matches decision 46 literally, but couples the rewrite schema to `kraken-model` while that is changing, and the generic shape has no second user yet.
- **Commands registered by `kraken-rewrite`, or the registry depending on it.** See above: a cycle or a surface that can forget.
- **Unicorn as the emulator.** GPL-2.0-only; cannot be combined.
- **Running the original natively as the only oracle.** Catches emulator bugs, but only works on same-architecture hosts and needs a sandboxed process per case for arbitrary binaries. It stays as a future kind.
- **Letting `rewrite_function` run unconfined behind a flag.** Convenient on hosts without Landlock, and exactly the case where the risk is highest. Refused.
- **Agents may accept.** Acceptance is the human judgement that a verdict is enough; same rule as proposals (ADR 0005).
- **Letting a repair attempt replace the failed version.** Versions are append-only and a failed attempt is evidence; the history of what the model got wrong is worth keeping, and nothing is lost by storing it.
- **A `stale` lifecycle status.** It would have to be set and cleared by events and would hide the real status (a stale accepted unit is still accepted until a person decides). A flag computed from hashes cannot get out of step.
- **Translating whole programs in one model call.** Does not fit in a context window, and a failure has no location. Functions in dependency order give bounded prompts and local failures.
